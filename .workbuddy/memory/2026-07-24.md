## 第 7 段纠正:产品逻辑正确,挂起是测试基建问题(已改写独立用例)
- 用修正后的 `openSkillsPanel`(先点 launcher 打开 Chat)隔离跑 `skill-tabs-repro`,**通过**:plan→available / link→changed;切 link→link→available / plan→changed。`validate-final` 也证明状态算对了。即 **DESIGN §10 业务逻辑没问题**,早先"产品死循环"判断推翻。
- 全量 e2e 第 7 段挂起的真因是**测试基建**:同一 `page`/`worker` 跨 6 段累积状态 + MV3 SW 空闲被 stop 后,捕获一次的 `worker` 句柄变 stale,`worker.evaluate` 卡到 600s protocolTimeout(无 30s 超时,故表现为"挂死"而非抛错)。`skill-tabs-repro` 因每次 `freshWorker()` 重取句柄故不卡。
- 按用户要求:**不动原有 `chrome-extension.mjs` / `skill-tabs-repro.mjs`(已 git checkout / 手动还原)**,改为新增独立用例 `tests/e2e/business-tab-source-status.mjs`:自包含 Chrome 启动(env 门控 `--no-sandbox`、`E2E_HEADLESS`)、内嵌 `skill-source-tabs` fixture、`freshWorker` 重取 SW、正确 `openSkillsPanel`(点 launcher)、`makeLocatorDerivedSkill`、断言 plan/link 在切 Tab 后 available↔changed 翻转。`E2E_HEADLESS=1 E2E_NO_SANDBOX=1` 实跑 **通过(EXIT 0)**,约 7s。新增 npm script `test:e2e:business-tab`。

- **business-tab 挂起根因(已用 skill-tabs-repro.mjs 隔离复现确认)**:`skill-source-tabs` 页面带 2 个 locator 派生技能(均 autoRunEnabled:false)时,`derived-column` 运行时调度器陷入 MutationObserver 反馈死循环 —— `[web2ai.derived-runtime] schedule → schedule-skip-auto-disabled`(每技能)反复触发,刷屏并占满主线程。repro 自带诊断显示 `validate-final` 状态本身算对了(plan=available、link=changed),但技能面板永不收敛,`waitForSkillStatusClass` 30s 超时 → `[repro] FAILED: Waiting failed: 30000ms exceeded`。结论:产品缺陷(调度器/observer 反馈环),非测试断言错误;测试期望完全符合 DESIGN §10。修复方向:derived-column 调度器对 auto-disabled 技能不应反复 reschedule,且 observer 回调须去抖,避免渲染→mutation→schedule 的环。e2e 第 7 段挂死、第 8 段(multi-table fallback)未执行皆源于此。
